## 1. Executive summary

The shared focus manager was exercised with the exact Case Details dialog markup and its current `setupModal` configuration. Focus entry, Tab and Shift+Tab containment, background-focus redirection, close-button handling, focus restoration, and repeated open/close cycles passed in the component fixture at four widths and both themes. Escape did **not** close Case Details in all eight runs. Source inspection explains why: `setupCustomModalFocus` prevents Escape and invokes an optional callback, but `cases.js` does not supply `onEscape` when it configures this dialog. This is a confirmed Case Details keyboard defect. Add Case supplies an Escape callback in `components/add-case/add-case.js`; its authenticated Dashboard flow and nested native IO dialog were not run.

All Cases, FIR Index, Admin Users, the nested FIR accused table, and the Dashboard chart region were checked in static fixtures using application markup/classes and CSS, with synthetic rows where needed. The horizontal regions were focusable and showed focus outlines. They overflowed horizontally without creating page-wide overflow. With a settled browser measurement, ArrowRight moved the region in 23/24 table fixture runs and all 6 chart runs; ArrowLeft moved it back in all 24 table and all 6 chart runs. One All Cases 320px dark-theme first press did not move; in five repeated attempts, the first did not move and the next four did. This isolated inconsistency is not classified as a confirmed defect. Fixture-only evidence does not close UX-009 or UX-014.

No application behavior was changed. No authenticated session, Firebase service, emulator, production endpoint, credential, or existing browser profile was used.

## 4. UX-003 findings

The source-based fixture called the actual `setupModal` and `setupCustomModalFocus` implementations from `assets/js/shared-utils.js`, with the current Case Details initial/fallback focus options. It used the exact Case Details modal markup from `pages/cases.html` and no replacement focus-trap logic.

| Viewport | Theme | Initial focus inside | Tab / Shift+Tab contained | Background focus redirected | Escape closes | Close button restores opener | Repeated cycles |
|---:|---|---|---|---|---|---|---|
| 320px | Dark | Pass | Pass / Pass | Pass | **Fail** | Pass | Pass |
| 320px | Light | Pass | Pass / Pass | Pass | **Fail** | Pass | Pass |
| 375px | Dark | Pass | Pass / Pass | Pass | **Fail** | Pass | Pass |
| 375px | Light | Pass | Pass / Pass | Pass | **Fail** | Pass | Pass |
| 768px | Dark | Pass | Pass / Pass | Pass | **Fail** | Pass | Pass |
| 768px | Light | Pass | Pass / Pass | Pass | **Fail** | Pass | Pass |
| 1366px | Dark | Pass | Pass / Pass | Pass | **Fail** | Pass | Pass |
| 1366px | Light | Pass | Pass / Pass | Pass | **Fail** | Pass | Pass |

**Root cause:** `setupCustomModalFocus` handles Escape by preventing default/propagation and calling `onEscape?.()`. Case Details calls `setupModal(detailsModal, ..., { initialFocusSelector, fallbackFocusSelector })` without an `onEscape` callback. Thus Escape is consumed while the modal stays open. The same helper is configured with an `onEscape` callback for Add Case, but its full authenticated open/close and nested IO behavior remain unverified.

**Classification: PARTIALLY VERIFIED.** The shared component logic and Case Details configuration were exercised in an isolated fixture, confirming the Escape failure. Authenticated route behavior, Add Case integration, dynamic controls, and nested native dialog interactions remain untested. The defect is reproducible in the actual component logic and is reported without implementing a fix.

## 5. UX-009 findings

The three static table fixtures used the current page markup, current CSS, and two synthetic rows. The nested accused-table fixture used the current generated wrapper semantics/class and current CSS; its generator was inspected but not executed. Each was measured at 320px, 375px and 430px in dark and light themes (24 fixture combinations total).

Representative 320px measurements (scroll width / client width):

| Table | Scroll width / client width | Focus target | ArrowRight from start | ArrowLeft from far edge |
|---|---:|---|---:|---:|
| All Cases | 1190 / 318px | Focusable, solid outline | 0px in one dark-theme run; repeated 5 times: first press 0px, next four 40px | Moved back 40px in the repeated check |
| FIR Index | 720 / 320px | Focusable, solid outline | 40px | 40px |
| Admin Users | 960 / 320px | Focusable, solid outline | 40px | 40px |
| Nested FIR accused table | 1180 / 304px | Focusable, solid outline | 40px | 40px |

At 375px and 430px, all table regions had overflow and all completed ArrowLeft checks moved back from the far edge. Across the full matrix, ArrowRight moved in 23/24 runs; ArrowLeft moved in 24/24. These are short browser key steps, not evidence that every hidden column was exposed with a single press. The scroll extent and previously hidden content were present in the measured overflow region. No fixture had page-wide horizontal overflow. Shift+Wheel was tested as a supplementary pointer-assisted action; it moved 18/24 table fixture cases and is not counted as keyboard verification.

The single All Cases first-press miss was not stable across repeated tries and does not establish a production defect. No JavaScript keyboard-scroll handler exists; native Chrome behavior is the tested mechanism.

**Classification: PARTIALLY VERIFIED.** Native keyboard scrolling, focus semantics and horizontal overflow worked in the static fixtures. Actual table routes, generated FIR table integration, live rows, touch behavior, and keyboard access to row actions remain unverified. The one inconsistent first press is recorded as inconclusive rather than a confirmed defect.

## 6. UX-014 findings

The real chart scroll-region/SVG markup and Dashboard CSS were tested at 320px, 375px and 430px in both themes (6 static fixture combinations). The synthetic fixture did not load `dashboard.js`, chart data, or a chart library renderer.

At 320px, the region measured `scrollWidth=720px`, `clientWidth=320px`, and `max scrollLeft=400px`; at 375px and 430px the 720px SVG remained wider than its region. The focusable region showed a solid visible focus outline. ArrowRight moved 40px from the start and ArrowLeft moved 40px back from the far edge in all 6 cases. No fixture produced page-wide overflow. Shift+Wheel did not move the chart region in 0/6 cases. The chart region had its accessible label, and the SVG carried its own accessible name. Rendered legend readability, actual SVG labels, interactive chart controls, and data/legend association were not tested because the renderer was not running.

**Classification: PARTIALLY VERIFIED.** Region focus, native horizontal keyboard movement and overflow are demonstrated in a static fixture; actual chart rendering, legend accessibility/readability, period interaction, and authenticated Dashboard behavior remain unverified.
