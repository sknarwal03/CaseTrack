# Password Setup B4.2 — Final Technical Approval Package

**Purpose:** Owner review of the exact B4.2 attestation design only. This document is a proposed specification and approval checklist, not implementation authorization. No application code, Firestore data, Rules, indexes, configuration, dependencies, or deployment are changed. UX-001 remains **Critical · Open**.

**Reviewed source:** `PASSWORD-SETUP-B4-EXACT-APPROVAL-MATRIX.md`, `PASSWORD-SETUP-B4-SECURITY-DESIGN.md`, `PASSWORD-SETUP-API-CONTRACT.md`, `PASSWORD-SETUP-SECURITY-REVIEW.md`, current Admin middleware/UI, role data, token helper, Firebase config and Rules. Current source has no recovery attestation endpoint. Admin auth verifies ID token revocation and current active role, but no recent `auth_time` gate. The Admin UI's password login and settings code use Firebase email/password provider; settings already uses `reauthenticateWithCredential`. Current Users rows expose UID, role, status and station ID; no email will be added.

## 1. Decisions Evaluated

The following are suitable B4.2 decisions, subject to the exact schema/API approval checklist at the end:

1. Create a B4.2-only recovery operation record with only attestation fields; defer issue/handoff/reconciliation fields.
2. Attestation valid for **10 minutes**, measured from trusted server `verificationAt`; endpoint rejects expired operations. This period applies to later authorized use of that attestation and does not extend the 5-minute reauthentication requirement.
3. No `relatedOperationId` in B4.2. It is not needed for a first attestation. Defer links between reissue/reconciliation operations to B4.5 if required.
4. Persist accepted audit event atomically with operation/idempotency record. Application code never updates/deletes audit events. This is application-level append-only, not immutable against privileged project/service-account administrators.
5. Audit retention policy is 365 days. Do not add TTL, scheduled deletion, or other deletion behavior in B4.2. Obtain separate retention implementation approval; legal-hold and records policy owners must be identified before deletion is designed.
6. Defer `operatorRecoveryIssuanceLimits` and `recoveryOperationId` on `operatorSetupActionCodes/{uid}` to B4.3/B4.5. B4.2 does not issue or revoke tokens.
7. Require verified Firebase ID-token `auth_time` with `0 <= nowSeconds - auth_time <= 300`. Reject absent, non-integer, future, stale claims. Do not substitute `iat`, client timestamps, or token refresh.
8. Require genuine Firebase Auth reauthentication using the account's supported provider. Current app uses email/password. UI sends the password only to Firebase Auth SDK, never to a Functions endpoint. If an account's provider is not supported by the UI, fail closed and stop the attestation workflow.
9. Target confirmation displays exactly UID, role, status, and police station ID from trusted role data. No email. The endpoint independently fetches Auth and role state.
10. Require explicit `verificationAcknowledged: true`; server fixes method to `in_person` and records server time. This records Admin attestation, not proof that an in-person meeting happened.
11. Leave `resetOperatorPassword`, temporary-password provisioning, and role assignment unchanged.
12. Only active, globally authorized Admins can create or replay an attestation. The target must be an enabled Auth user and an active Operator with `mustChangePassword === false`.

## 2. B4.2 Firestore Schemas

### 2.1 Recovery operation

**Path:** `operatorRecoveryOperations/{operationId}`. ID is a server-generated UUID v4. Admin SDK only. Current client Rules catch-all remains unchanged and denies clients. Functions are the sole application writer. The authenticated Admin is the actor; the backend derives UID from verified token claims. Operation and audit/idempotency records have no automatic deletion in B4.2. Their retention beyond the approved audit period requires a separate decision.

| Field | Type | Required | Value / source |
|---|---|---:|---|
| `operationId` | string | Yes | UUID v4; equals document ID; generated by server |
| `actionType` | string enum | Yes | `recovery_verification` only in B4.2 |
| `state` | string enum | Yes | `attested` only on successful creation; expiry is derived from timestamp, not a stored state |
| `actorAdminUid` | string | Yes | UID from verified Firebase ID token |
| `targetOperatorUid` | string | Yes | Target UID validated and checked by backend |
| `reasonCode` | string enum | Yes | `operator_lost_access` only in B4.2 |
| `verificationMethod` | string enum | Yes | Server-fixed `in_person` |
| `verificationAcknowledged` | boolean | Yes | `true` only; false/missing rejected |
| `verificationAt` | Firestore Timestamp | Yes | Trusted server time |
| `attestationExpiresAt` | Firestore Timestamp | Yes | `verificationAt + 10 minutes` |
| `createdAt` | Firestore Timestamp | Yes | Firestore server timestamp |
| `updatedAt` | Firestore Timestamp | Yes | Firestore server timestamp; equals creation time on initial write |

No token, token digest, recovery URL, password, email, bearer header, request body, or client timestamp is stored. No B4.3+ fields (`tokenIssuedAt`, `tokenExpiresAt`, handoff fields, revocation fields, `relatedOperationId`) are part of the B4.2 schema.

### 2.2 Idempotency record

**Path:** `operatorRecoveryIdempotency/{keyDigest}`. This is a new B4.2 collection, Admin SDK only, and must be explicitly approved with the operation schema. Deterministic document ID prevents concurrent use of the same client key from creating multiple operations without a query/index. `keyDigest = SHA-256(UTF-8("casetrack:operator-recovery-idempotency:v1:" + canonicalKey))` using lowercase hex. Never store raw key.

| Field | Type | Required | Value / source |
|---|---|---:|---|
| `keyDigest` | string | Yes | 64-char lowercase SHA-256; equals document ID |
| `actorAdminUid` | string | Yes | Verified Admin UID; binding |
| `targetOperatorUid` | string | Yes | Validated target UID; binding |
| `requestFingerprint` | string | Yes | 64-char lowercase SHA-256 of canonical B4.2 request |
| `createdAt` | Firestore Timestamp | Yes | Firestore server timestamp |
| `expiresAt` | Firestore Timestamp | Yes | `createdAt + 24 hours`; replay window, not a deletion instruction |
| `operationId` | string | Yes | Original operation UUID v4 reference |

**Canonical key:** HTTP `Idempotency-Key`, canonical lowercase RFC 4122 UUID v4 only; exact regex `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. Reject missing, uppercase/noncanonical, malformed, or non-v4 keys with `400 invalid-idempotency-key`. Generate a fresh cryptographically random UUID v4 when the Admin opens a new confirmation attempt; preserve that same key for retries of that attempt.

**Canonical fingerprint input:** fixed-order UTF-8 JSON with no whitespace and no normalization:

```json
{"action":"recovery_verification","reasonCode":"operator_lost_access","targetOperatorUid":"<validated uid>","verificationAcknowledged":true,"version":1}
```

`requestFingerprint = SHA-256(UTF-8(canonical JSON))`, lowercase hex. Include every body value that affects operation semantics. Actor is separately bound in `actorAdminUid`; idempotency document ID is bound to key digest. No credentials or secret values enter the fingerprint.

**Replay retention:** same response may be replayed only during the 24-hour window. After `expiresAt`, return `409 idempotency-key-expired`, never create a replacement operation using that key. Since B4.2 must not implement TTL/deletion, expired idempotency records remain as tombstones until a separate retention/deletion approval; keys are never reusable. This means records can accumulate and retain UID bindings longer than 24 hours; owner must accept this or separately approve a safe cleanup policy before implementation. Audit documents remain subject to the 365-day policy, but B4.2 does not delete them.

### 2.3 Audit event

**Path:** `operatorRecoveryOperations/{operationId}/events/{eventId}`. UUID v4 ID, server-generated. Accepted event is created atomically with operation and idempotency record. App code creates but never updates/deletes events. Functions runtime service identity requires least privilege consistent with its other Admin SDK responsibilities; Google Cloud project IAM administrators remain able to alter records. Current Firestore Rules deny client reads/writes. B4.2 provides no Admin UI audit browsing endpoint and no client read permission. Audit read access is restricted to authorized operators through separately managed Google Cloud/IAM access; exact human groups and legal hold policy require owner assignment. No TTL/deletion in B4.2.

| Field | Type | Required | Value / source |
|---|---|---:|---|
| `eventId` | string | Yes | UUID v4; equals document ID |
| `eventType` | string enum | Yes | `attestation_accepted` for persisted B4.2 events |
| `actorAdminUid` | string | Yes | Verified active Admin UID |
| `targetOperatorUid` | string | Yes | Validated and server-checked target UID |
| `operationId` | string | Yes | Parent operation ID |
| `reasonCode` | string enum | Yes | `operator_lost_access` |
| `verificationMethod` | string enum | Yes | `in_person` |
| `verificationAt` | Firestore Timestamp | Yes | Same trusted server time as operation |
| `eventAt` | Firestore Timestamp | Yes | Firestore server timestamp |
| `outcome` | string enum | Yes | `accepted` |

**Defined event/result vocabulary:** `attestation_accepted`, `attestation_rejected`, `authorization_denied`, `target_unavailable`, `storage_failure`. Only `attestation_accepted` is written as a durable event in B4.2 because it has a valid operation path and is atomic with the accepted operation. Rejected/pre-operation outcomes are recorded as minimal structured Cloud Logging events (fixed event code, function name, result, generated correlation ID, latency; actor UID only if verified and permitted by logging policy). Do not write rejected/anonymous attempts into a client-selectable Firestore path. No unauthenticated write primitive or separate security-event collection is introduced. Logging is operational observability, not a substitute for durable audit. Never log token, password, Authorization header, request body, email, or raw Firebase error object. If storage fails after verified auth, emit `storage_failure` to structured logs and return 503; do not create an operation without its accepted audit event.

**Retention decision:** policy is 365 days. B4.2 must not implement TTL, scheduled deletion, manual deletion, or legal-hold bypass. Before any deletion mechanism, obtain separate approval from the records/legal owner for holds, access, and deletion semantics. If no retention owner or hold process is identified, keep data and do not delete.

## 3. API Contract — B4.2 Only

### `POST /recordOperatorRecoveryVerification`

**Deployment form (when separately implemented):** Firebase Functions v2 HTTPS `onRequest`, region `us-central1`. No function export or production deployment is authorized by this package.

**Request headers:**

- `Authorization: Bearer <Firebase ID token>`
- `Content-Type: application/json`
- `Idempotency-Key: <canonical lowercase UUID v4>`
- Browser `Origin` must match the existing exact Admin allowlist; CORS is not authentication.

**Request JSON, exact keys:**

```json
{
  "targetUid": "<Firebase Auth UID>",
  "verificationAcknowledged": true,
  "reasonCode": "operator_lost_access"
}
```

No unknown keys. `targetUid` must match `^[A-Za-z0-9_-]{1,128}$`; acknowledgement must be boolean `true`; reason must exactly equal `operator_lost_access`. No actor UID, role, email, method, time, password, token, token purpose, or client-generated operation ID accepted. Maximum request body: **4096 bytes**. Reject malformed JSON, non-object/array, extra/missing keys and oversized input before storage work.

**Success:** `201 Created`, JSON:

```json
{
  "operationId": "<server UUID v4>",
  "verificationExpiresAt": "<ISO-8601 UTC timestamp>"
}
```

Headers include `Cache-Control: no-store, max-age=0`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`, `Vary: Origin`; allow only the exact configured origin, POST, and `Authorization`, `Content-Type`, `Idempotency-Key`. `OPTIONS` preflight returns 204 and no body. No wildcard CORS. Every error response also uses no-store headers. The API returns no target email, token, link, credential, or sensitive role detail.

**Response/status contract:**

| HTTP | Error code | Behavior |
|---:|---|---|
| 201 | — | New accepted operation, or same-key/same-request replay within 24h returns the original `operationId` and same `verificationExpiresAt`; replay response uses 200 (see below) |
| 200 | — | Idempotent replay of the original successful result; no new operation/event |
| 400 | `invalid-request` | Malformed body, wrong/missing fields, invalid UID syntax, false/missing acknowledgement, unsupported reason |
| 400 | `invalid-idempotency-key` | Missing or invalid/noncanonical UUID v4 header |
| 401 | `unauthorized` | Missing, invalid, expired or revoked ID token; disabled Admin account; absent/future/stale `auth_time` |
| 403 | `forbidden` | Authenticated caller lacks current active Admin role |
| 403 | `forbidden` | Request Origin is not allowlisted; do not return `Access-Control-Allow-Origin` |
| 404 | `operator-unavailable` | Target missing, disabled, not an active Operator, or `mustChangePassword !== false`; same generic response for all target eligibility failures |
| 409 | `idempotency-conflict` | Existing key digest has different actor binding, target binding, or request fingerprint |
| 409 | `idempotency-key-expired` | Same key mapping exists but 24-hour response-replay window passed; no new operation |
| 413 | `request-too-large` | Body exceeds 4096 bytes |
| 415 | `unsupported-media-type` | Request is not JSON |
| 405 | `method-not-allowed` | Method other than POST or valid OPTIONS preflight |
| 429 | — | **Not defined in B4.2.** No verification-attempt throttle is implemented or implied |
| 500 | `temporarily-unavailable` | Unexpected internal failure; generic body only |
| 503 | `temporarily-unavailable` | Auth/Firestore dependency unavailable or commit outcome unresolved; client retries same key only; no second operation is created |

Valid allowlisted `OPTIONS` preflight returns `204 No Content`; invalid preflight returns 403. Never treat CORS as authentication. A disallowed origin receives no allow-origin header.

### Authentication, authorization and eligibility

1. Parse one Bearer token and verify it with Firebase Admin `verifyIdToken(token, true)` (revocation check). Explicitly reject disabled Admin Auth users. Actor UID comes only from verified claims.
2. Require `auth_time` to be an integer NumericDate in seconds and enforce `0 <= floor(serverNowMs/1000) - auth_time <= 300`. Missing, future or older-than-300-second values fail closed. Never trust `iat`, a request timestamp, or client state.
3. Re-read `userRoles/{actorUid}` and require `role=admin`, `status=active`, `mustChangePassword !== true`, and no `policeStationId` assignment. Recheck role within the Firestore transaction. Every request/replay requires current authorization and recent reauthentication.
4. Fetch target with Firebase Admin Auth; require enabled account. Read `userRoles/{targetUid}` and require `role=operator`, `status=active`, and `mustChangePassword === false`. No role, station, status, Auth password or other account data is changed. Auth enabled state cannot be transactionally locked with Firestore; check immediately before transaction and treat the attestation as invalid if disabled is observed.

### Idempotency and atomicity

- For a new key, compute namespaced key digest and canonical fingerprint. In one Firestore transaction, read the deterministic idempotency document, the current Admin role, target role, and all operation/event references before writes. If no idempotency doc exists and checks pass, create operation, accepted audit event and idempotency record atomically.
- If the key document exists and binding+fingerprint match, return the original successful response with HTTP 200 while within 24h; do not write another event or operation. If actor, target, or fingerprint differs, return 409 without disclosing prior operation details.
- Concurrent identical submissions serialize on the deterministic idempotency document. Exactly one creates the operation; the other transaction retries, observes the committed mapping, and returns the same result. Concurrent same-key/different-request submissions produce one winner; all conflicting requests receive 409.
- After a lost HTTP response, caller retries the same request with the same key; the committed mapping recovers the original operation ID/expiry. If still indeterminate/unavailable, return 503 and instruct retry with the same key. Never advise generating a new key for an uncertain result.
- The UI keeps the key stable for that pending confirmation attempt. It must not silently generate a new key on network retry. If page/session loss destroys the key, require Admin to restart selection/confirmation/reauthentication as a fresh explicit attempt; no token issuance occurs in B4.2.
- A durable operation, accepted audit event, and idempotency mapping are one transaction. Any failure before commit creates none of these. If commit result is ambiguous, the deterministic key mapping is the reconciliation path; no second key is created automatically.
- Idempotency records are replayable for 24h and retained as non-reusable tombstones after the replay window because deletion/TTL is not approved. This creates indefinite metadata retention until separate cleanup approval; explicit owner acceptance is required.

## 4. B4.2 UI Scope

The Admin Panel change is limited to a new recovery-verification/attestation UI; it does not issue, reveal, copy, deliver, or acknowledge a recovery token/link.

1. **Select Operator:** enable action only for a selected candidate, but treat UI role/status as advisory.
2. **Confirm trusted target:** fetch server-backed details and display only UID, role, status, police station ID. Confirm action is bound to that UID. Do not display or add email.
3. **Reauthenticate Admin:** provider-aware Firebase reauthentication. Current app login is email/password; use Firebase `EmailAuthProvider`/`reauthenticateWithCredential`. Send password only to Firebase Auth SDK. After success, obtain a fresh ID token; backend still verifies `auth_time`.
4. **Confirm in-person verification:** explicit checkbox/affirmation that Admin verified the person in person and matched the intended Operator account; explain that this is an Admin attestation.
5. **Select approved reason:** B4.2 permits only `operator_lost_access`; do not offer consuming review or general-purpose free text.
6. **Submit:** create one UUID v4 idempotency key per confirmation attempt; submit exact body/header. Disable duplicate button while pending. Retry ambiguous network result only with same key/body.
7. **Display result:** only confirmed `201/200` displays operation ID and expiry. Provide safe messages for unauthorized/stale session, target unavailable, idempotency conflict/expired, invalid input and service failure. Never imply password changed or link issued. No email, token, password or recovery URL UI.

## 5. Security Invariants and Boundaries

- B4.2 creates a verification record only; no token minting/validation/completion/revocation, password mutation, role mutation, or credential provisioning.
- Active Admin status is revalidated server-side; client roles and actor IDs are ignored.
- Reauthentication is genuine and recent; no refresh-only or client-timestamp workaround.
- Target data is server-verified; display is confirmation only, not authorization.
- Exact idempotency key/fingerprint is hashed at rest; no raw key is persisted. Keys are not credentials but are still not logged.
- Only accepted operation events are durable in this B4.2 design. No unauthenticated Firestore write path. Rejections use minimal structured operational logs, not a claimed immutable audit event.
- Audit application writes are append-only; privileged IAM can still alter data. Read access is not granted to clients. No TTL/deletion implementation until separately approved.
- Operation/event/idempotency writes are atomic; Firebase Auth and Firestore are not a cross-service transaction. No password or Auth change is part of this increment.
- Existing temporary-password provisioning, initial setup flow, token registry, Firestore Rules, indexes and production configuration remain unchanged.

## 8. Emulator Test Requirements (for a separately approved implementation)

Use Firebase Auth and Firestore Emulators with synthetic Admin/Operator users only. No real credentials or production project. Test:

1. Valid active Admin, recent `auth_time`, enabled eligible target and acknowledgement create exactly one operation, accepted event and idempotency record.
2. `auth_time` at exactly 300 seconds accepted; 301 seconds, future, missing, wrong type rejected. Revoked/disabled Admin rejected; active role removed/changed rejected.
3. Invalid token, non-Admin, inactive Admin, `mustChangePassword:true`, station-assigned Admin denied; no operation/event/idempotency data is created.
4. Target missing, disabled, admin-role, revoked/inactive operator, or `mustChangePassword:true` returns uniform `operator-unavailable`; no accepted durable records.
5. Missing/false acknowledgement, unsupported reason, missing/extra fields, malformed JSON, invalid UID, invalid UUID, oversized/non-JSON body and wrong method behave exactly per contract.
6. Same key + same canonical request returns same operation ID and expiry within 24h; does not duplicate event or extend expiry. Same key with different target/reason/ack or different verified Admin returns 409 and leaks no mapping.
7. Concurrent duplicate requests create one operation/event/idempotency document and return one stable result. Concurrent different bodies sharing one key produce one winner and conflict for other request.
8. Lost response simulation after Firestore commit, followed by same-key retry, recovers original response. Commit uncertainty plus unavailable Firestore returns 503 without generating a second key/operation.
9. At 24h boundary replay is expired; same key is not reusable; no automatic deletion occurs. Test record remains as tombstone.
10. Firestore transaction failure/audit write failure creates no partial operation or idempotency record. Storage failure is secret-free in logs and generic to caller.
11. Verify CORS preflight/allowlist, no-store headers on all responses, request body limits and no token/password/header/body logging.
12. Verify target confirmation UI fields and provider reauthentication; verify no recovery token issuance/display, no Auth password update, no role mutation, and temporary-password workflow regression.
13. Emulator restart persistence: committed operation/audit/idempotency records remain across emulator export/import or persisted emulator restart; document environment limitations.

Do not claim an emulator proves production IAM, audit immutability, clock synchronization, or cross-service Auth/Firestore atomicity.
